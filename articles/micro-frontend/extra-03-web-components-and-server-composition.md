# 番外篇三：Web Components 与服务端组合，为什么它们没有成为主流

**核心要点：**

- Web Components 的理论吸引力：浏览器原生标准、Shadow DOM 天然样式隔离、框架无关、不依赖任何运行时框架——纸面上是微前端的「长期主义答案」
- 落地落差在哪：样式隔离过强（主题与设计系统穿透难，CSS Variables 都进不去）、数据传递繁琐（attribute 只能传字符串、property 与 attribute 的心智负担）、SSR/hydration 支持参差、调试体验差
- React 生态的态度演变：React 19 对自定义元素的支持明显改善（属性透传、事件监听），但状态管理与事件模型的摩擦仍在——主流框架不冷不热，WC 就难成主力
- 服务端组合的另一条路线：ESI 边缘组装、BFF 聚合多应用模板、Islands 架构（Astro 为代表）——在服务端完成页面组合，客户端拿到完整页面再局部激活
- 服务端组合的适用边界：内容型站点、SEO 强诉求、首屏性能敏感的场景很合适；交互密集的中后台（频繁状态联动、复杂路由）短板明显
- 为什么两者都没成微前端主流：微前端的核心痛点是「存量异构系统的渐进整合」，而 Web Components 要求按标准重写组件、服务端组合要求重构部署架构——都要求「按它们的方式重来」，恰好与「不动存量」的诉求相反
- 但它们没有死：设计系统与跨团队组件分发（WC）、SSR 组合与 Islands（服务端路线）在各自场景活跃——它们是「隔离与协作边界」的另一种答案，值得放进选型全景（对照第三篇）
