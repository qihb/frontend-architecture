# 番外篇二：从 JS Bundle 到 Single-SPA，微前端运行时方案是怎么演进的

**核心要点：**

- 早期形态 JS Bundle 直塞：script 标签按需加载子应用产物，能跑，但全局污染、无生命周期、依赖冲突三大问题无解——「能组合」不等于「可协作」
- Single-SPA 的奠基性抽象：应用注册表 + 生命周期协议（bootstrap/mount/unmount）+ 激活函数，第一次把「应用」变成浏览器里的可挂载、可卸载单元，是后来所有运行时方案的概念地基
- 应用加载的演进：SystemJS + import maps 的模块加载 → HTML Entry（qiankun 的关键创新：以 HTML 为入口的资产自描述，子应用构建产物自包含）——加载方式决定了接入成本
- 沙箱的演进：SnapshotSandbox 快照恢复（性能差、不支持多实例）→ LegacySandbox → ProxySandbox（代理 window，多实例共存），隔离强度与浏览器兼容的权衡（对照第四篇三代沙箱）
- Single-SPA 的局限为什么催生 qiankun：协议太底层、样板代码多、隔离与样式要自己拼——qiankun 的价值不在新协议，而在「把散件工程化封装成开箱即用」
- 演进主线一条：从「能组合」到「隔离强、接入易、性能优」，每一代方案都在重新移动「隔离与协作的边界」——理解这条线，才能判断新方案该不该跟进
